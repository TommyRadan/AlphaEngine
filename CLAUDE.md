# CLAUDE.md

This file orients a contributor working in this repository: what AlphaEngine is, how to build, run and check it, how the modules relate, and the conventions the code follows. It describes the architecture as it stands today; a detail that belongs to one feature, not the architecture, lives in a doxygen comment next to that code instead of here.

AlphaEngine is a C++20, single-executable real-time 3D engine. `runtime::engine` owns the SDL3-backed platform layer (`platform`: the window, input and the audio device), a Vulkan renderer (`rendering_engine`), Jolt Physics (`runtime::physics`), embedded Lua scripting via sol2 (`runtime/scripting`), and a scene graph of pooled nodes and components; gameplay is added through self-registering game modules under `external/`. It targets Windows (MSVC) and Linux (GCC/Clang). There is no separate editor build and no `docs/` tree — the debug-only Dear ImGui overlay and gizmos of the `editor/` module are the closest thing to an editor, and reference material lives in doxygen comments next to the code they document.

## Build, run and check

- **Windows:** `./scripts/build.ps1` auto-detects the toolchain: MSVC via vcpkg at `C:\vcpkg` (the setup `scripts/setup-windows.ps1` produces), falling back to MSYS2 UCRT64 (Ninja + g++) at `C:\msys64`. Flags: `-Toolchain msvc|msys2`, `-Configuration Debug|Release|RelWithDebInfo|MinSizeRel` (default `Release`), `-Clean`.
- **Direct CMake (MSVC + vcpkg):**
  ```
  cmake -S . -B build -G "Visual Studio 17 2022" -A x64 \
    -DCMAKE_TOOLCHAIN_FILE=C:/vcpkg/scripts/buildsystems/vcpkg.cmake
  cmake --build build --config Release
  ```
- **Linux (Ninja):**
  ```
  cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_COMPILER=gcc -DCMAKE_CXX_COMPILER=g++
  cmake --build build --target AlphaEngine -j2
  ```
  Clang builds the same way with `-DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++ -DCMAKE_CXX_FLAGS=-stdlib=libc++`; CI builds both. The default build builds `AlphaEngine` alone; `cmake --build build --target alpha_demos` builds the showcase executables (see `external` below), and CI builds both.
- **Output:** `Binaries/AlphaEngine.exe` (Ninja) or `Binaries/<Configuration>/AlphaEngine.exe` (the Visual Studio generator) on Windows; `Binaries/AlphaEngine` on Linux; the showcases as `alpha_demo_<name>` beside it.
- **The Vulkan SDK is a required build dependency on every platform**: `find_package(Vulkan REQUIRED)` runs unconditionally, and the Vulkan backend at `rendering_engine/gpu/backend/vulkan/` is the only GPU backend (`rendering_engine::graphics_settings::backend` — the engine's `settings->graphics.backend` — the `ALPHAENGINE_GRAPHICS_BACKEND` env var, or `--backend`, which accept `vulkan` and warn about any other value).
- SDL3, GLM, nlohmann/json (backs `settings.json`), glslang (GLSL → SPIR-V for the Vulkan backend), the Vulkan Memory Allocator, Dear ImGui + ImGuizmo (Debug builds only), Jolt Physics, KTX-Software (KTX2 texture loading) and Lua + sol2 are all fetched from source by CMake via `FetchContent`; no system package is needed for any of them. stb and cgltf (vendored, header-only) round out the stack.
- **Format and naming gates**, both run in CI on Linux with clang-format/clang-tidy 18:
  - `./scripts/check-style.ps1` (`-Fix` to rewrite in place) runs clang-format over every `.cpp`/`.hpp`/`.h` under `runtime/`, `core/`, `platform/`, `assets/`, `rendering_engine/`, `editor/`, `external/`. See `.clang-format` (Allman braces, 4-space indent, 120 columns, pointer-left).
  - `./scripts/check-naming.ps1` (`-Fix` to apply renames) configures a Ninja `build-tidy/` directory for `compile_commands.json`, then runs clang-tidy's `readability-identifier-naming` check over the same seven directories. See `.clang-tidy` (snake_case).
  - The Linux equivalents (what CI actually runs):
    ```
    find core platform runtime assets rendering_engine editor external -type f \( -name '*.cpp' -o -name '*.hpp' \) \
      | xargs clang-format-18 --style=file --dry-run -Werror
    cmake -S . -B build-tidy -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_EXPORT_COMPILE_COMMANDS=ON \
      -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++
    run-clang-tidy-18 -p build-tidy -quiet "(runtime|core|platform|assets|rendering_engine|editor|external)/"
    ```
  - Every source, shader, CMake, script and workflow file under `core/`, `platform/`, `runtime/`, `assets/`, `rendering_engine/`, `editor/`, `external/`, `shaders/`, `cmake/`, `scripts/`, the root `CMakeLists.txt` and `.github/workflows/` must start with the SPDX header (see Conventions below); CI checks this alongside clang-format.
- **Headless smoke run:** a Debug binary can run with no real display or GPU, on Mesa's lavapipe software Vulkan implementation with the Khronos validation layer, for a bounded number of frames:
  ```
  export VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation \
    ALPHAENGINE_GRAPHICS_BACKEND=vulkan SDL_AUDIO_DRIVER=dummy
  xvfb-run -a ./Binaries/AlphaEngine --width 640 --height 360 --frames 300 --fail-on-error
  ```
  `--fail-on-error` makes the run exit non-zero on any `[ERR]`/`[FTL]` log line, so a validation message fails it even without a crash. Add `VK_LAYER_ENABLES=VK_VALIDATION_FEATURE_ENABLE_SYNCHRONIZATION_VALIDATION_EXT` to the environment for the synchronization-validation variant. There is no `docs/` directory and no unit or functional test suite; this smoke run is the runtime check.

## Module map

Each module builds as a static library: `alpha_core` (`core/`), `alpha_platform` (`platform/`), `alpha_assets` (`assets/`), `alpha_rhi` (`rendering_engine/gpu/`), `alpha_render` (the rest of `rendering_engine/`), `alpha_world` (`runtime/`) and `alpha_editor` (`editor/`), each linking the modules and third-party libraries it uses, as the root `CMakeLists.txt` states (see Dependency rules below). An executable is built from `alpha_game`, an object library with the entry point (`runtime/main_loop.cpp`), the game-module API and the modules every game shares, plus its own game modules (see `external` below).

### `core`

The foundation module, in plain C++ with no SDL; nothing here depends on `platform`, `assets`, `runtime`, `rendering_engine` or `external` (see Dependency rules below). It holds: math (`core::math` — `vec2`/`vec3`/`vec4`, `mat3`/`mat4`, `quat`, and snake_case free functions `dot`, `cross`, `normalize`, `length`, `lerp`, `look_at`, `perspective`, `ortho`, `translate`, `rotate`, `scale`, `inverse`, `transpose` — thin GLM wrappers with identical memory layout, so a GLSL uniform upload uses `value.data()` — plus the angle constants every module shares, `pi`, `two_pi` and `half_pi` (`core/math/constants.hpp`)); logging (`core/log.hpp`, see Conventions; it writes to stderr and to whatever `core::logging::sink`s are added through `add_sink`); the generic settings machinery (`core::settings_registry`, resolved once by `core::load_settings` from compiled defaults, then `<pref path>/settings.json`, then `ALPHAENGINE_*` environment variables, then the command line, each layer overriding the last) that every module's own settings section registers against — `platform::window_settings`; `rendering_engine`'s graphics, camera, shadow and post-process settings; `core::input_settings`; and the content-root, diagnostics and time-scale settings `runtime::engine_settings` bundles; `core::time` (on `std::chrono::steady_clock`; every duration in seconds as a `double` — the frame's delta scaled by the game time scale, the unscaled real delta, the fixed step and the total time — plus the time scale itself, 0 meaning paused, and the fixed-step accumulator); the slot-allocated `core::pool<T>` container; `core::event_bus`, a process-wide synchronous typed publish/subscribe hub (`subscribe<E>`, `emit<E>`, `enqueue<E>`, `flush`; reentrant, main-thread-only); `core::job_pool`, a worker pool for background dispatch and the one subsystem that is itself thread-safe; `core::input` (up to `input_settings::max_players` local players, each with its own action/axis state read from the keyboard, mouse or gamepad devices assigned to it — the keyboard and mouse start on player 0, where the single-player API with no player argument reads; a gamepad is assigned by platform joystick id, automatically to the first free player on connect or explicitly through `assign_gamepad`, and remembers its player across a disconnect; `rebind_action`/`rebind_axis` replace one player's bindings for an already-registered name, `listen_for_next_input` drives that from the next input one of the player's own devices reports, and `load_user_bindings`/`save_user_bindings` read and write those per-player rebinds as JSON at a caller-given path); `core::audio` (a software mixer, voices, listeners and a clip cache, with no dependency on the renderer, playing and decoding through the `core::audio_output` / `core::audio_decoder` interfaces in `core/audio/audio_backend.hpp` that the engine fills with the platform's); `core::vfs` (the mount points the asset loaders and the script host read files through); and `core::os` (the OS services core itself needs, on the C++ standard library alone: file I/O, UTF-8 paths, reading the environment, local time, the crash handler, directory-watch polling).

### `platform`

Where the engine talks to the OS through SDL3, in namespace `platform`; it depends on `core` only. (The editor's ImGui overlay is the one other SDL3 user, through ImGui's own SDL3 backend.) `platform::window` (`platform/window.hpp`) creates the Vulkan-capable window from `platform::window_settings` (size, fullscreen / borderless mode, resolving a zero size against the display) and pumps the OS event queue once per rendered frame, translating keyboard, mouse, text, window and gamepad events into `core` events on the bus it is handed (`platform/sdl_input.hpp` holds the pure key / button / axis translation). Every event passes the window's event filter first (`set_event_filter`), which reports the input classes it captures; the editor installs it so a focused ImGui panel keeps its input from the game. The window also supplies what the GPU device needs to present — its native handle, a Vulkan surface factory and the instance extensions — which the engine hands to the device as a `gpu::surface_desc`. `platform/audio_device.hpp` implements `core::audio`'s playback device and WAV decoder over SDL's audio streams; `platform/platform.hpp` provides the executable and per-user preference directories (`base_path`, `pref_path`), the discovered content root (`content_root`), setting an environment variable, and `install_log_sinks`, which adds the `engine.log` mirror beside the executable and routes SDL's own diagnostics into the log under the `sdl` category; `platform/dynamic_library.hpp` loads shared libraries.

### `assets`

The CPU asset module (namespace `assets`): decoders and importers that turn files, read through `core::vfs`, into plain data, with no dependency on the renderer, the GPU device or `runtime`. It holds `image` (RGBA8 pixels, decoded by stb_image), `color` and `color_space` (the colour space an image was authored in); `font` (a TrueType face packed into a glyph atlas by stb_truetype, with glyph metrics and kerning); `decode_texture_file` / `decode_ktx2` (`texture_decode.hpp`: PNG / JPEG through stb_image, KTX2 through libktx, Basis Universal transcoded to the best family in a `compressed_format_support` the caller captured from the device); the vertex structs and `vertex_format` (`vertex.hpp`), `mesh_data` (layout-agnostic interleaved vertex bytes, indices and object-space bounds) and `generate_tangents`; the procedural mesh generators (`mesh_generators.hpp`, namespace `assets::mesh_generators`: one parameter struct per primitive shape — `box`, `capsule`, `circle`, `cubed_sphere`, `cylinder` (and `cone()`), `plane`, `polyhedron` (and the four platonic solids), `ring`, `sphere`, `torus` — that `generate` turns into `mesh_data` and `cache_key` into the structural key an asset cache holds it under); `cache_key_number` (`cache_key.hpp`, the locale-independent text of a number in such a key); and the glTF 2.0 importer (`gltf_importer.hpp`, via the vendored `cgltf`), whose `import_gltf` produces a `gltf_document` — `mesh_data` per primitive keyed by the file's canonical identity, material descriptions (factors plus texture references), textures and image references with their decoded pixels, the node hierarchy, skins and animation channels. Nothing here touches the device, so the asset cache runs its decodes and imports on the job pool.

### `runtime`

The composition root and world model. `runtime::engine` (`runtime/engine.hpp`) owns every subsystem as a `std::unique_ptr`, in dependency order, and publishes itself through `runtime::current_engine()`; `engine::init()` brings each subsystem up (events, audio, input, the VFS mount, the window, the GPU device against the window's surface, the renderer, the overlay, the asset cache, physics, scripting, the scenes), adds the engine's own systems to the scheduler, then installs the game modules; `runtime/main_loop.cpp`'s loop calls `engine::tick()` until `is_quit_requested()` is true, and the destructor tears every subsystem down in reverse. **The frame is an explicit schedule**: `runtime::scheduler` (`runtime/scheduler.hpp`, owned as `engine::systems`) runs named stages in a fixed order — `input`; the fixed stage, once per fixed step, as `scripts_fixed` → `physics` → `post_physics`; `update`; `animation`; `transform_propagation`; `audio`; `render_extract` — and a system is a named function of the frame's `runtime::frame_time` (seconds: the fixed step or the frame's scaled delta, the unscaled delta, the time scale, the interpolation alpha) added to one stage with `scheduler::add(stage, name, fn, {order, while_paused})`, which returns an RAII `runtime::system_registration`. Within a stage systems run by order, then in the order they were added; the engine's own systems use the orders in `runtime::engine_order`, and game code adds its own systems the same way, so what runs when never depends on the order anything subscribed to an event in (the event bus carries input, window, collision and quit events, not ticks). The time scale (the `time.scale` setting, `core::time::set_time_scale` / `set_paused`, Lua's `time.scale` / `time.paused`, the editor's Profiler panel) scales the delta the fixed-step accumulator is fed, so it thins out or stops the fixed steps; while it is 0 the scheduler also skips every system not added with `while_paused` (behaviours' updates, animation, physics interpolation), so the frame loop, the input, the editor and the UI keep running. Every stage and system run is timed (`scheduler::stage_timings`, `system_timings`), and the Profiler panel shows the figures. A `runtime::overlay` (`runtime/overlay.hpp`) is a tool layer drawn over every frame that the executable hands the engine through `engine::set_overlay` before `init` — `main` installs the editor there in Debug builds — so the engine drives it without depending on it: it comes up right after the renderer, starts each rendered frame before the render extraction (`begin_frame`, where it may edit nodes) and finishes it right after (`end_frame`, where it may read the proxies just written), before the renderer records, and goes down before the renderer. `runtime::scene` is the scene graph: `runtime::node` (a pooled, stable-address transform hierarchy) and per-type-pooled components (`runtime::component_handle`, `runtime::component_store`) — any default- and copy/move-constructible struct can be a component with no registration, and one that defines `on_fixed_update(node&)` or `on_update(node&)` gets it called once per fixed step or once per rendered frame, in type order, parents before children (the scene's walks: `scene::fixed_update`, `scene::update`, and `scene::propagate_transforms`, which only settles the world matrices; `scene::each_visited<C>` visits one type in the same order). The renderer sees a scene's meshes, lights and cameras only through **render extraction** (`runtime/render_extraction.hpp`): `runtime::extract_render_proxies(scene_manager&)`, run in the scheduler's `render_extract` stage once per rendered frame, after every update and right before the renderer, walks each scene's `light_component`, `camera_component`, `mesh_component`, `renderable_component` and `ui_element_component` pools and has each write its proxy in the scene's `render_world` — a light's or camera's settings every frame; a pose (from the node's world matrix, for a camera composed with the component's `offset`) only when the node's world-matrix stamp (`core::transform::get_world_version`) moved; a `renderable_component`'s `rendering_engine::mesh_source` description, with an instanced source's changed instance records and draw arguments, only when the source's revision moved; a skinned mesh's joint palette, which `animator_component` hands the `mesh_component` (`set_joint_matrices`), only when a new one was set; and a `ui_element_component`'s `rendering_engine::ui_element` quads only when the element's revision moved. The components own their settings objects (`rendering_engine::light`, `rendering_engine::camera`) or what they draw (a `mesh_asset` and a material, a `mesh_source` or a `ui_element`) and a proxy handle, never a render object with a transform: they create the proxy in `on_attach`, destroy it in `on_destroy`, and follow the node's active state in `on_active_changed` (a light or camera is disabled and enabled again; a mesh or UI proxy is destroyed and created again, last), so a proxy's order in the world — and a UI element's paint order — is the order those hooks ran in. Right after the extraction, the same stage has the overlay finish its frame (`runtime::overlay::end_frame`): the editor draws its light and camera gizmos from the proxies just written, and the physics wireframe from the physics world, through the immediate-mode debug-draw functions. `runtime::behavior` is game logic attached through a `behavior_component`, with `on_enable`/`on_start`/`on_fixed_update`/`on_update`/`on_disable`/`on_destroy` lifecycle hooks; both update hooks take seconds of game time and run in hierarchy order (every loaded scene in turn, depth-first, parents before children), whatever order the behaviours were attached in. A structural change from inside a hook — destroying a node, removing a component, reparenting, enabling or disabling a subtree — must go through the scene's deferred commands (`destroy_node`, `defer_remove_component<C>`, `defer_reparent`, `defer_set_active`), which the scheduler applies (`scene::apply_deferred`, through `scene_manager::apply_deferred`) after every fixed step and after the update, so a node destroyed in `on_fixed_update` is gone, rigid body included, before the next fixed step; the immediate APIs refuse otherwise. `runtime::scene_manager` loads, unloads, enables and updates every scene (the persistent one plus whatever else is loaded); `runtime/scene_serializer.hpp` (`save_scene`, `load_scene`) saves and loads a scene or a subtree as JSON — scene files and prefabs; `REFLECT_TYPES()` and `runtime::type_builder<T>` (`runtime/reflection.hpp`; `registry.register_component<C>("name")` / `register_behavior<B>("name")`) let a component or behaviour declare the fields a scene file should carry; the engine's own types are registered by `runtime::default_type_registry` when it is first used (`register_component_types`, `register_lua_behavior`), because a `REFLECT_TYPES()` block is a static initialiser, which the linker drops with any object of a static library that nothing references. `runtime::physics::world` (`runtime/physics/`) wraps Jolt Physics, stepped at the fixed rate in the scheduler's `physics` stage. `runtime::animation` (`runtime/animation/`) holds `skeleton` and `animation_clip`, the CPU data and sampling behind skinned meshes, which `animator_component` drives (advanced once per fixed step in `post_physics`, its pose sampled between the last two steps in the `animation` stage) and `runtime::instantiate_gltf` builds from an imported document's skins and animations. Lua 5.4 is embedded through sol2 under `runtime/scripting/`: `runtime::lua_behavior` is an ordinary `behavior` whose hooks forward to a script loaded through the VFS. `runtime::instantiate_gltf` (`runtime/gltf_instantiate.hpp`) spawns nodes and components from an imported glTF model: the CPU document plus the meshes and materials uploaded from it.

### `rendering_engine`

Owns the ordered list of render passes, through `rendering_engine::renderer` (`renderer.hpp`), itself owned by `runtime::engine`, which also owns the GPU device and brings it up before the renderer. The engine hands `renderer::init` a `render_services` (`render_services.hpp`) naming every subsystem the renderer works through (the device, the window, the event bus, the job pool, the asset cache, the clock) and read-only views of the settings it reads, and the renderer keeps it until `quit`. `renderer::render()` walks its pass list twice per frame — every enabled pass's `prepare`, then every enabled pass's `record` — inside `gpu::device::begin_frame`/`end_frame`, handing every pass the same per-frame `frame_context` (the active camera's proxy, the enabled light proxies, the frame's scene, overlay and UI draws, the tool overlay, viewport, frame index, clock, TAA jitter and a snapshot of the settings) so passes cannot disagree mid-frame; the scene pass renders into an off-screen HDR target, a post chain (tonemap, and depending on settings bloom, TAA, FXAA, motion blur, auto-exposure and volumetric fog) resolves it to LDR, and the UI pass composites on top. Every pass, the built-in ones included, enters the list through `renderer::add_pass(std::unique_ptr<pass>, pass_placement)` (`passes/pass_list.hpp`): at the end of a `render_stage` (`shadow`, `scene`, `post`, `ui`, `overlay`) or right before or after a pass already in the list, named by its `pass::name` (`builtin_passes` in `passes/pass.hpp`), never at an index; `renderer::init` registers the default chain that way, and engine, game or tool code adds its own passes, `remove_pass`es or `set_pass_enabled`s any pass between frames without an edit to the renderer, which keeps no pointer to a pass. No pass holds a pointer to another either: everything they hand each other travels through the frame's **resource store** (`passes/resource_store.hpp`), which the renderer owns and hands every pass as `frame_context::resources` — it clears it and publishes its own targets (the swapchain, the HDR scene colour and its depth, the LDR target, the grading LUT) at the top of each frame, then each pass looks up in its `prepare` what the passes before it published and publishes what it produces (a pass that republishes a name, as motion blur does the scene colour, hands the passes after it a new version) under typed `resource_key`s (the renderer's and the built-in passes' are in `passes/frame_resources.hpp`: the shadow maps with their fits, the scene pass's per-frame groups and draw list, motion vectors, the TAA resolve, the eye adaptation). `pass::declare_io` names, by the same keys, what a pass reads (required, optional, or unordered: a history or a value a later pass prepares) and writes; the list validates that order whenever it changes (an error asserts in Debug builds), and Debug builds report any publish or lookup a pass did not declare. `render_world` (`render_world.hpp`), owned by the renderer, owns what a frame draws: the debug-draw list and the **proxies** (`render_proxies.hpp`, `mesh_proxy.hpp`, `ui_proxy.hpp`) — plain copies of what the world places, held in `core::dense_pool`s (dense, in creation order, addressed by generational handles): `mesh_proxy` (a `mesh_description` — the geometry as a shared `mesh_asset`, the material, object-space bounds, layer bits, shadow flag, whether it is instanced and whether the debug overlay draws it instead of the scene passes — plus the world matrix with the PerDraw block, mirror flag and world bounds derived from it, a visibility flag, an instanced proxy's snapshot of instance records and indirect draw arguments, and a skinned proxy's joint palette), in the order the scene, depth pre-pass and shadow passes (or, for an overlay proxy, the debug pass) walk them; `ui_proxy` (a UI element's quads grouped by the texture they sample, with the ui material they draw with and a revision), in the order they paint in; `light_proxy` (kind, colour and intensity, world position and direction, range and attenuation, cone angles, shadow flag), with the enabled lights kept in the order they were enabled, which is the order the scene pass packs them in; and `camera_proxy` (world matrix, view, projection, frustum, culling mask, priority, main tag, enabled flag), over which the world arbitrates the active camera (highest priority, then the main tag, then the most recently created). Whoever owns a proxy creates, enables and destroys it through the world's handle API and writes it before the frame; the passes read only proxies, never the objects they were copied from — the active camera and the enabled lights reach them through `frame_context`, and so do the mesh proxies, as the frame's draw lists (`frame_context::scene_draws`, one `mesh_draw` per scene proxy that each pass culls by view and pass kind, and `frame_context::overlay_draws`, which the debug pass draws on top), and the UI proxies, as the UI pass's draws (`frame_context::ui_draws`, one per quad group, in paint order). The renderer's `mesh_draw_builder` (`mesh_draws.hpp`) and `ui_draw_builder` (`ui_draws.hpp`) build them once per frame inside the device's frame bracket, uploading the instance snapshots, joint palettes and UI quads into the per-proxy GPU buffers they keep; no pass reads a node, a component, a mesh source, a UI element or the physics world, and the world refuses to create or destroy a proxy while a frame is recorded. Each `runtime::scene` points to the `render_world` it feeds — set by the scene manager as the scene is created — so the components reach it through `scene::world()` rather than a global.

- **`gpu/`** — the backend-agnostic RHI: `gpu::device`, `command_encoder`, `pipeline`, `bind_group`, `buffer`, `texture`, `handle`, and `gpu::create_device(backend_type)`, which builds the implementation under `gpu/backend/vulkan/` (VMA-backed sub-allocation, a staging ring for uploads, the per-draw block in push constants). There `vk_device` is a facade over one component per responsibility, each with its own header: `vk_instance` (instance, debug messenger, surface), `vk_physical_device` and `vk_logical_device` (GPU selection, feature and format negotiation, the queues, the allocator, device loss), `vk_pipeline_cache`, `vk_transfer` (transfer batches and the staging ring), `vk_frame` (frames in flight, their fences, per-frame command pools and secondary-recording lanes, and the deferred-destroy queue gated on submission serials), `vk_descriptor_allocator`, `vk_query_pool`, `vk_swapchain` (acquire, present, suspend and recover) and `vk_render_pass_cache`; `vk_device` owns them as members in bring-up order and `vk_device::quit` shuts them down explicitly, while the resource tables (`vk_resources.hpp`) stay its members, with a `vk_device_*.cpp` per resource family. The component headers are internal to the backend. `gpu::device::init` takes a `gpu::surface_desc` (`gpu/surface.hpp`: the native window handle and the window system's Vulkan surface factory, its instance extensions, the drawable size and the vsync preference) and the frame-slot count, so the backend never looks the window up; later drawable sizes arrive through `resize_swapchain`. Shader compilation (`shader_compiler`, GLSL → SPIR-V via glslang) and lookup (`shader_library`) live here too, as does `gpu::overlay_renderer` (`gpu/overlay_renderer.hpp`), the GPU half of the Dear ImGui overlay: `device::create_overlay_renderer` builds the backend's (the Vulkan one, `vk_overlay_renderer.cpp`, owns every `ImGui_ImplVulkan_*` call and rebuilds its pipeline when the swapchain pass changes), and the debug pass records the overlay's frame through it; it exists only in builds that link ImGui.
- **`passes/`** (+ `passes/post/`) — the `rendering_engine::pass` interface and `frame_context` (`pass.hpp`), the ordered `pass_list` with its stages and placements (`pass_list.hpp`), the per-frame `resource_store` and pass declarations (`resource_store.hpp`) with the built-in resource keys (`frame_resources.hpp`), and one type per render pass (`scene_pass`, `shadow_pass`/`point_shadow_pass`/`spot_shadow_pass`, `depth_prepass`, `skybox_pass`, `ui_pass`, and the post passes).
- **`materials/`** — a `material_template` per material type (its shaders, layouts, and a cache of pipeline variants) shared by any number of `material` instances; eight built-in types (`basic`, `phong`, `standard`, `instanced`, `points`, `line`, `grid`, `ui`).
- **`renderables/`** (+ `premade_2d/`) — what is drawn: the mesh sources (`mesh_source.hpp`) a `runtime::renderable_component` puts in a scene — `instanced_mesh`, `line` and `points` — which describe their geometry and material for a mesh proxy and upload the geometry when it is set (a line or a point cloud uploads a private `mesh_asset` on every change; an instanced mesh keeps its instance records for the extraction to capture); and the UI elements (`premade_2d/ui_element.hpp`) a `runtime::ui_element_component` puts in a scene — `sprite_batch` (quads grouped by texture), and the `pane` and `label` widgets built on it — which keep their quads on the CPU and hand them over through `capture()` when their revision moved. Each takes what it works through from its creator at construction: the `gpu::device` it uploads to (a line, a point cloud, an instanced mesh's private geometry, a pane's own image). A primitive shape is no renderable of its own: an `assets::mesh_generators` shape fetched through `asset_cache::get_or_create_mesh` is a shared `mesh_asset` that a `runtime::mesh_component` draws like any other mesh.
- **`resources/`** — the GPU side of asset loading: `asset_cache`, a reference-counted, deduplicating store that uploads what the `assets` module decodes — textures (`texture_asset`, KTX2 transcode targets picked from what the device samples), fonts (`font_asset`, the glyph atlas) and meshes (`mesh_asset`, which keeps its CPU-side bounds; `get_or_create_mesh` caches procedural geometry under a structural key, building it only on a miss — handed an `assets::mesh_generators` shape it takes the key and the builder from the generators; `upload_mesh` uploads one outside the cache, for geometry an object uploads for itself) — with asynchronous loads decoded on the job pool and uploaded in `asset_cache::pump`, and debug-build texture hot reload. It gets its `gpu::device` (and the renderer glTF materials are built through) from `runtime::engine` at `init`, and every asset releases its GPU resource on that device. `gltf_model.hpp` turns an imported `assets::gltf_document` into a `gltf_model` (`upload_gltf`: the meshes and textures through the cache, one `standard_material` per material description), synchronously (`asset_cache::load_gltf`) or in the background (`asset_cache::load_gltf_async`).
- **`debug_draw/`** — debug geometry, in namespace `rendering_engine::debug_draw`. The immediate-mode API (`debug_draw.hpp`: `line`, `box` (axis-aligned, or oriented by a transform), `sphere`, `axes`, `grid`, `frustum`, `arrow`, `text`, in the style of Unreal's `DrawDebugLine` and Unity's Gizmos): called every frame something should show, each takes the `render_world` to record into, a colour, a duration in seconds of world time (0 draws for the one frame) and, except `text`, depth-test on or off; there is no object to create or keep. It records into the world's `debug_draw::draw_list` (`draw_list.hpp`), which `engine::tick` ages once per tick (dropping what expired) before anything records. At the start of `renderer::render()`, before the frame opens, the renderer's `line_batches` turn the live segments into two line proxies on `layer_editor`, with no bounds and no shadow — the on-top segments one overlay proxy the debug pass draws, the depth-tested ones one scene proxy the scene pass draws (a depth-testing, non-writing line material of its own) — each re-uploaded only when its segments changed and present only while it has any; the editor draws the text labels over the frame with ImGui. Outside Debug builds `debug_draw::enabled` is false and every function compiles to nothing. Besides that: the depth-tested `infinite_grid`, the editor's ground grid (a mesh proxy on `layer_editor`, with no bounds and no shadow, that the scene pass draws, shown or hidden through `renderer::editor_grid()`), and `debug_pass`, the always-on-top swapchain pass that draws the overlay mesh proxies and then the editor's ImGui overlay. The debug pass is registered, in the `overlay` stage, only in Debug builds, and the grid and the line batches exist only there too.
- **`lighting/`** — `ambient_light`, `directional_light`, `point_light`, `spot_light` (a light's settings, with no pose; `copy_light_settings` and `place_light` turn settings and a world matrix into a `light_proxy`), `environment_probe`.
- **`camera/`** — `camera`, `perspective_camera`, `orthographic_camera`: a camera's lens (the projection) and its rank (enabled, priority, main tag, culling mask), with no pose; `view_matrix_from_world` derives a view from a camera's world matrix.

### `editor`

The debug editor, in namespace `editor`, a module of its own above `runtime`, `rendering_engine` and `platform`: a Dear ImGui + ImGuizmo overlay compiled only with `ALPHAENGINE_HAS_IMGUI` (Debug builds; every translation unit compiles to nothing otherwise). `editor::create_overlay()` (`editor/editor.hpp`) returns it as a `runtime::overlay`, and `runtime/main_loop.cpp` installs it on the engine. The editor object, `editor::editor_layer` (`editor/editor_layer.hpp`), owns the ImGui context, the SDL3 platform backend, the GPU device's `gpu::overlay_renderer` (handed to the renderer for the debug pass to record) and the state of every panel; `editor.cpp` is the core (context, backends, the window's event filter so a focused panel keeps its input from the game, the dockspace and the per-frame build: `begin_frame` builds the panels before the render extraction, `end_frame` draws the debug visualisations after it and ends the ImGui frame), and each panel is a file of its own: the FPS overlay whose context menu toggles the rest, Hierarchy, Inspector, the transform gizmo, Console, Render Targets, Profiler (the game's pause and time-scale controls, the frame-time graph, the CPU time of every scheduler stage and system, the GPU time of every pass), Scene statistics, Settings, Post and Helpers. The editor runs on real time, so it stays responsive while the game is paused. `debug_visuals.cpp` records the built-in debug visualisations through the debug-draw functions every frame — the world axes and the physics wireframe (on by default), a gizmo per enabled directional, point and spot light and the frustum of every enabled camera but the rendering one (off by default) — as the Helpers panel's toggles (with the ground grid's) select, and draws the debug-draw text labels, projected through the active camera, on ImGui's foreground draw list.

### `external`

Gameplay code as self-registering **game modules**: one translation unit each, using `GAME_MODULE() { ... }` from `external/api/game_module.hpp`, compiled straight into an executable (the registration is a static initialiser, which a static library would drop): `alpha_game` holds the entry point, the game-module API and the `camera_module` and `exit_module` every game shares, `AlphaEngine` adds the shadow, physics and UI demos, and each other showcase (fog, glTF, instancing, lines, Phong, points, a colour-tint post pass registered from the module, scene graph, skybox) places its geometry at the origin and so is an executable of its own, `alpha_demo_<name>`. The macro registers a bootstrap that the engine calls once, after every subsystem is up, with the active `runtime::scene&`, to spawn nodes, attach components and `runtime::add_behavior<B>(node, ...)` instances; a module names its behaviours in a `REFLECT_TYPES()` block so scene files can carry them. Modules include `core/`, `assets/`, `runtime/` and `rendering_engine/` headers directly rather than through a separate facade; `external/api/` supplies only the `GAME_MODULE()` bootstrap macro (`external/api/log.hpp` and `external/api/time.hpp` declare a small logging/timing surface that nothing in the tree currently calls).

### `shaders`

GLSL under `shaders/` (`include/` for shared `#include`-able pieces, `materials/` for the eight built-in materials, `passes/` for the pass stages), authored as Vulkan-style GLSL (`#version 450`, explicit `layout(set, binding)` on every resource). `shaders/CMakeLists.txt` lists every file explicitly; `cmake/embed_shaders.cmake` embeds them into the `shader_registry` static library at build time, served by `gpu::shader_library::source(path)`; `cmake/generate_shader_bindings.cmake` generates `include/bindings.glsl` from `rendering_engine/gpu/shader_bindings.hpp`, so the binding numbers have one owner. Compiled SPIR-V is cached on disk under `<pref path>/shader_cache/` (`ALPHAENGINE_SHADER_CACHE` disables it or redirects it).

### Dependency rules

The root `CMakeLists.txt` states these rules as the modules' links. A module's public headers use the types of the modules it links `PUBLIC`, so those reach its dependents as well: `runtime` sees the `gpu::` interface through the renderer. The build enforces them: before a module compiles, its include check (`cmake/module_includes.cmake`) resolves every first-party header its sources include and fails the build, naming the file and line, on a header of a module that its links do not reach.

- `core` depends on nothing else in the tree — it is the foundation every other module builds on. Where it needs an OS service it declares an interface or hook and the engine wires the platform's implementation in: log sinks (`core::logging::add_sink`, `forward`, `set_level_observer`), the audio output and decoder, and the preference directory handed to `core::load_settings`.
- `platform` depends only on `core` (and SDL3), and `rendering_engine` does not depend on it: the engine hands the renderer the drawable's size and the aspect that stands in for an empty drawable as values in its `render_services`, the UI rect helpers take sizes, and the GPU device gets its surface as a `gpu::surface_desc`, its shader-cache directory through `gpu::set_default_shader_cache_directory` and a validation layer bundled beside the executable through `VK_LAYER_PATH`, all of which the engine sets up from the platform before the device comes up.
- `rendering_engine/gpu/` depends on `core` alone (plus Vulkan, VMA and glslang); nothing in it includes the rest of `rendering_engine`, which builds on it. One documented exception: in Debug builds it links ImGui, privately, because the Vulkan backend holds ImGui's Vulkan renderer behind `gpu::overlay_renderer`, so the editor draws its overlay without naming a graphics API. Every GPU backend carries its own ImGui renderer the same way.
- `assets` depends on `core` alone (plus the vendored stb and cgltf, and libktx): no `rendering_engine`, `gpu`, renderer or `runtime` include and no `runtime::current_engine()`, so a tool, a world system or a worker thread can decode and import without the renderer. `rendering_engine`, `runtime` and `external` build on it.
- `runtime` depends on `rendering_engine`, not the reverse: `runtime/components` attaches `rendering_engine` types (materials, mesh sources, UI elements, cameras, lights) to nodes and the engine owns the renderer, the GPU device and the asset cache, while nothing under `rendering_engine/` includes a `runtime/` header or calls `runtime::current_engine()`. `rendering_engine` receives what it works through by injection: the renderer gets its subsystems and settings in the `render_services` handed to `renderer::init` and builds its passes against its device (the scene pass also against the job pool); a line, point cloud, instanced mesh or pane, or an `environment_probe`, takes the device from its creator at construction; and the asset cache takes its device and renderer at `init`. `runtime::physics::world` does not depend on `rendering_engine`: it fits colliders to the CPU-side bounds of what a node draws (`runtime/components/drawn_bounds.hpp`), and debug builds draw its colliders through the debug-draw functions (`runtime::physics::draw_debug`, `runtime/physics/physics_debug_draw.hpp`), which the editor calls after the render extraction; the renderer never reads the physics world.
- `editor` depends on `core`, `platform`, `runtime` and `rendering_engine` (plus ImGui, ImGuizmo and, through ImGui's platform backend, SDL3); nothing in them includes `editor/`, and only the executable's `main` creates it. It reaches the engine through the `runtime::engine&` its `init` is handed, not through `runtime::current_engine()`.
- `external` depends on `core`, `assets`, `runtime` and `rendering_engine`; nothing in those four depends on `external`.
- **GLM types and functions are named only inside `core/math/`.** Every other module reaches vectors, matrices and quaternions through `core::math`.

## Frame lifecycle

`runtime::engine::tick()` runs once per iteration of the main loop: it advances the clock (`core::time::perform_tick`, so this tick's deltas describe the frame about to run), runs the scheduler's frame (`scheduler::run_frame`), then, unless the window is minimized, its `render_extract` stage (`scheduler::run_render_extract`) and the renderer, and finally, when `settings->diagnostics.frame_limit` is non-zero and reached, requests quit (`core::quit_requested`). The engine's systems (each named, with its order, in `runtime::engine_order`), stage by stage:

1. **`input`** — in Debug builds first age the world's debug-draw list by the frame's game time, dropping what expired (`debug_draw::draw_list::advance`); pump OS and window events onto the bus (`platform::window::tick`), latch this frame's cursor motion (`core::input::end_frame`), deliver the events buffered since the last tick (`core::event_bus::flush`), and upload the asynchronous asset loads whose decode has finished (`asset_cache::pump`).
2. **The fixed stage**, decoupled from the render rate: the frame's scaled delta feeds the accumulator, and for each fixed step it drains (zero, one or several per frame): **`scripts_fixed`** latches the step's input edges (`core::input::begin_step`) and runs every scene's `on_fixed_update` hooks (`scene_manager::fixed_update`, so every enabled `behavior::on_fixed_update`, in hierarchy order); **`physics`** steps the simulation (`runtime::physics::world::step`); **`post_physics`** advances every animator by the step, then applies every scene's deferred commands and pending unloads (`scene_manager::apply_deferred`).
3. **`update`** — interpolate the simulated nodes between the last two steps (`runtime::physics::world::interpolate`) so they move smoothly at the render rate; in Debug builds poll the scripts for hot reload; spawn the glTF models pending in `instantiate_gltf_when_ready`; run every scene's `on_update` hooks (`scene_manager::update`: every enabled `behavior::on_update`, in hierarchy order, and any other component's `on_update`); apply the deferred commands again.
4. **`animation`** — every animator writes its pose, sampled between the last two fixed steps.
5. **`transform_propagation`** — every scene settles its world matrices (`scene_manager::propagate_transforms`).
6. **`audio`** — hand the listeners' and sources' settled poses to the mixer, then mix (`core::audio::update`, on real time, its voices at the time scale); keeps playing while the window is minimized.
7. **`render_extract`** (only for a frame that is drawn) — build the installed overlay, the editor in Debug builds (`runtime::overlay::begin_frame`), which may edit nodes too; extract the frame's meshes, UI elements, lights and cameras, with instance records, joint palettes and UI quads, into the `render_world` (`runtime::extract_render_proxies`), so every pose and every piece of per-frame data the renderer reads comes from this one point; finish the overlay's frame (`runtime::overlay::end_frame`: the editor records its gizmos and the physics wireframe from the proxies just written through the debug-draw functions, draws the debug-draw text labels and ends its ImGui frame).
8. **Render** — `renderer::render()`: in Debug builds the debug-draw list becomes the debug line proxies, the pass list is validated again if a pass was added or removed since the last frame, the mesh and UI proxies become the frame's draw lists, the resource store is cleared and seeded with the renderer's targets, then every enabled pass's `prepare`, then every enabled pass's `record`, bracketed by `gpu::device::begin_frame`/`end_frame`; the device presents inside `end_frame`. The renderer runs on real time (`frame_context::time_seconds`, `delta_seconds`), whatever the time scale.

While the time scale is 0 the fixed steps do not run, and neither do the physics interpolation, the scene update's hooks or the animation; everything else does, so the input, the editor, the UI and the deferred commands keep going.

## Conventions

- `snake_case` for every identifier — namespaces, classes, structs, enums, functions, variables — including in game modules; only macros (`UPPER_CASE`) and template parameters (`CamelCase`) differ.
- Allman braces, 4-space indent, 120-column limit, pointer-left (`int* p`, not `int *p`). See `.clang-format`.
- Explicit file lists in every `target_sources()`/`add_library()` call — no `file(GLOB ...)`.
- Logging goes through `core/log.hpp`'s `LOG_TRC`/`LOG_DBG`/`LOG_INF`/`LOG_WRN`/`LOG_ERR`/`LOG_FTL` macros, never a raw `printf`, `std::cout` or SDL's logging API. Per-frame or per-draw output is `LOG_TRC` only, dropped before formatting unless trace is enabled. The active level comes from the build type (`debug` in Debug, `info` otherwise) and the `ALPHAENGINE_LOG_LEVEL` environment variable (e.g. `info,gpu=trace`); each translation unit sets `LOG_CATEGORY` (`engine` by default) before its first include. `LOG_FTL` logs and flushes but does not abort — the call site throws right after.
- **Comments** are doxygen (`@brief`, `@param`, ...) or an explanation of logic that is not obvious from the code around it; they describe the code as it is, never its history — no "was", "used to", "previously", "now", "no longer", "follow-up", and no issue or PR references, anywhere (code, comments, CMake, YAML, or this file). A detail a reader of the code needs belongs in a doxygen comment next to that code.
- Every new source, shader, CMake, script and workflow file starts with:
  ```
  // SPDX-License-Identifier: MIT
  // Copyright (c) 2015-2026 Tomislav Radanovic
  ```
  (`#` in place of `//` for CMake, YAML and shell/PowerShell files), followed by one blank line.
- Commits use Conventional-Commits-style prefixes (`feat:`, `fix:`, `refactor:`, `chore:`, `perf:`, `style:`, `docs:`, `ci:`, `cmake:`, `shaders:`, `scripts:`, `repo:`) with a lowercase imperative subject and, when the change needs explaining, a body wrapped at 72 columns that explains why rather than what. No attribution trailers. The repository is rebase-merged, so every commit must build on its own.
- Branches use `type/short-kebab-description` (e.g. `fix/log-va-list-forwarding`, `feature/fps-counter-overlay`).
- There is no `docs/` directory and no unit or functional test suite for now; the headless smoke run above is the runtime check, and this file is the architecture reference.

## How to

- **Add a source file or directory:** append the file to its directory's `CMakeLists.txt` (`target_sources(alpha_<module> PRIVATE ...)`, the module the directory belongs to); for a new directory, give it its own `CMakeLists.txt` and add `add_subdirectory(...)` to the parent's.
- **Add a render pass:** derive a type from `rendering_engine::pass` (`passes/pass.hpp`), give it a unique `name` and implement `record` (and `prepare`, `resize` or `declare_io` if the pass needs them) — a pass that owns GPU resources takes the `gpu::device` (`renderer::device()`) as its first constructor argument and keeps it; per-frame values arrive through `frame_context`, and what it reads from or hands to other passes through `frame_context::resources`, looked up and published in `prepare` under keys it also declares in `declare_io` — then register it with `renderer::add_pass(std::make_unique<your_pass>(...), pass_placement::before(builtin_passes::tonemap))` (or `in(render_stage::post)`, `after(...)`) from wherever it belongs: `renderer::init` for a built-in pass, a game module or tool otherwise (`external/post_tint_demo_module.cpp` registers one from a game module).
- **Add a material:** give the type (`materials/<name>_material.{hpp,cpp}`) a static `create_template(gpu::device&, ...)` that builds a `material_template`, and have `material_library::init` build and hold one instance; further instances share that template's pipeline cache.
- **Add a component:** any default- and copy/move-constructible struct works with no registration to exist on a node; give it an `on_update(node&)` method for per-frame logic (or `on_fixed_update(node&)` for per-fixed-step logic), attach it with `node::add_component<C>(value)`, and register it (`registry.register_component<C>("name")`, `runtime/reflection.hpp`) if scene files should be able to save and load it: an engine component in `runtime::register_component_types` (`runtime/components/component_types.cpp`), a game module's in its `REFLECT_TYPES()` block.
- **Draw debug geometry:** call the `rendering_engine::debug_draw` functions (`rendering_engine/debug_draw/debug_draw.hpp`) every frame the geometry should show — from a behaviour with `*owner().scene()->world()`, from a tool with `renderer->world()` — or once with a duration; they cost nothing outside Debug builds.
- **Add an editor panel:** declare a `draw_*_window()` member on `editor::editor_layer` with any state it keeps as members, define it in a file of its own under `editor/` (wrapped in `#ifdef ALPHAENGINE_HAS_IMGUI`, like the rest of the module), call it from `editor_layer::build_panels`, and give it a visibility flag in `panel_visibility` and an entry in the FPS overlay's menu.
- **Add a game module:** a new `.cpp` under `external/` with `GAME_MODULE() { ... }`, listed in `external/CMakeLists.txt` among the sources of the executable it belongs to (a showcase of its own is `<name>_demo_module.cpp`, with `<name>` added to `ALPHAENGINE_DEMOS` there); the body receives the active `runtime::scene&` to spawn nodes, attach components and `runtime::add_behavior<B>(node, ...)` instances, and may name behaviours in its own `REFLECT_TYPES()` block.
- **Add a script:** attach `runtime::add_behavior<runtime::lua_behavior>(node, "scripts/foo.lua")`; the script, read through the VFS, returns a table implementing any of `on_start`, `on_enable`, `on_disable`, `on_fixed_update(dt)`, `on_update(dt)`, `on_destroy` (`dt` in seconds of game time), and reads the clock through the `time` global (`time.delta`, `time.scale`, `time.paused`, ...).
- **Add a system:** `runtime::current_engine().systems->add(runtime::stage::update, "name", [](const runtime::frame_time& time) { ... }, {.order = ..., .while_paused = ...})` (`runtime/scheduler.hpp`) from whatever owns the logic, a behaviour say, which keeps the returned `runtime::system_registration`: the system runs once per frame (once per fixed step in a fixed stage) until the registration goes. Place it relative to the engine's systems with an order from `runtime::engine_order`; a system that must keep running while the game is paused (a tool, UI) sets `while_paused`.

## CI

`.github/workflows/ci.yml` runs on every push and pull request to `master`:

- **`format`** (Ubuntu) — clang-format 18 `--dry-run -Werror` over `core/`, `platform/`, `runtime/`, `assets/`, `rendering_engine/`, `editor/`, `external/`, plus the SPDX-header check over those directories and `shaders/`, `cmake/`, `scripts/`, `CMakeLists.txt` and `.github/workflows/`.
- **`tidy`** (Ubuntu, Clang 18 + libc++) — configures the tree for `compile_commands.json`, then runs `run-clang-tidy` (the `readability-identifier-naming` check) over `core/`, `platform/`, `runtime/`, `assets/`, `rendering_engine/`, `editor/`, `external/`.
- **`build-linux`** (matrix: GCC, Clang + libc++) — configures and builds the `AlphaEngine` and `alpha_demos` targets on both Linux toolchains; it does not run the binaries.
- **`smoke`** (matrix: plain, ASan+UBSan) — builds a Debug binary and runs it headlessly under `xvfb-run` on Mesa lavapipe with the Khronos validation layer, twice (once with synchronization validation added), 300 frames each, failing on any `[ERR]`/`[FTL]`/validation-layer line.
- **`build`** (Windows, matrix: Debug/Release) — installs the Vulkan SDK, builds `AlphaEngine` and then `alpha_demos` with MSVC, stages the Khronos validation layer next to a Debug binary, and uploads both configurations as workflow artifacts.
- **`comment-artifacts`** — posts, or updates, a sticky pull-request comment linking to the workflow run's uploaded artifacts.
